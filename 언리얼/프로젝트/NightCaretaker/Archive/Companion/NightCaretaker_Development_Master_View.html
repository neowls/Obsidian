수직 슬라이스 개발 기준

P0 목표는 관리실에서 민원을 접수하고, 도구를 챙기고, 현장 단서를 확인한 뒤 보고까지 완료되는 15~20분 루프를 실제 플레이 가능한 상태로 만드는 것이다.

핵심 루프접수 -> 도구 -> 이동 -> 단서 -> 판정 -> 조치 -> 보고
P0 민원OfficeLightBuzz, 203 Water, 302 TV Hum
중심 시스템Shift, Complaint Runtime, Evidence, Report, 307 Stage
완료 신호처음부터 끝까지 smoke-test route가 끊기지 않는다.

4. P0 Feature Backlog

각 기능은 플레이어 루프를 끊기지 않게 만드는 데 필요하다.

DEV-P0-01 Shift Bootstrap

PIE 시작 시 Chapter, ShiftPhase, 초기 민원 상태를 만든다.

DEV-P0-02 Complaint Data

P0 민원 3개를 DataAsset/DataTable 구조로 정규화한다.

DEV-P0-03 Complaint Board

관리실에서 Available 민원을 선택하고 FocusedComplaintId를 갱신한다.

DEV-P0-04 Evidence Actors

현장 상호작용이 AddEvidenceTag로 연결된다.

DEV-P0-05 Tool Selection

P0는 tag set 기반 보유 도구만 구현한다.

DEV-P0-06 Report UI

보고 결과가 SubmitReport, CloseComplaint로 이어진다.

DEV-P0-07 Room 307 Stage

Progression tag 기반으로 307 Stage 0~3을 계산한다.

DEV-P0-08 Lighting/Sound Hooks

공포 연출은 runtime state 또는 tag 후에만 발생한다.

DEV-P0-09 Save Checkpoint

보고 단위 임시 SaveGame으로 테스트 반복을 줄인다.

DEV-P0-10 Debug Commands

콘솔 명령으로 민원 상태와 증거/307 단계를 강제 전환한다.

6. Smoke Test

완료 기준은 문서가 아니라 PIE에서 관찰되는 플레이 흐름이다.

  1. 관리실 HUD와 reticle 표시 확인.
  2. 보드에서 CMP_PRO_OfficeLightBuzz 접수.
  3. 관리실 형광등 단서 확인, 조치, 보고.
  4. CMP_CH1_203_WaterAtDoor 접수.
  5. 도구 선택 후 203호 앞 단서 확인, 조치, 보고.
  6. CMP_CH2_302_TVHum 접수.
  7. 302호/3층 단서와 307호 쪽 잔류 사운드 확인.
  8. 보고 후 데모 종료 상태 진입.

7. Risks

P0에서는 기능 폭증보다 연결 완성도를 우선한다.

Enum mismatch

큰 진행 단계는 ChapterId/ProgressionTags로 처리하고 enum 증설은 보류한다.

UI owns state

UI는 subsystem/API만 호출하고 게임 상태를 직접 소유하지 않는다.

Hardcoded level events

상호작용 액터는 ComplaintId, EvidenceTag, ProgressionTag로 연결한다.

Tool scope creep

P0 도구는 tag set 기반으로만 구현한다.
