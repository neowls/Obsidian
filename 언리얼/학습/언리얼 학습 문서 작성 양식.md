# 언리얼 학습 문서 작성 양식

> [!summary] 요약
> 이 문서는 `언리얼/학습` 아래의 Unreal Engine 학습 Markdown 원본을 작성하거나 정리할 때 쓰는 표준 양식이다.
> 핵심 목표는 나중에 다시 열었을 때 기능의 정의, 쓰임, 작동 모델, 실패 시 확인 지점을 빠르게 복구하는 것이다.

## 핵심 결론

- 파일마다 `# 문서 제목`을 하나만 두고, 본문 섹션은 `##` 이하로 구성한다.
- 첫 화면에는 `[!summary]`와 `## 핵심 결론`을 둔다.
- 기술 설명은 `개요 -> 작동 모델 -> 주요 요소 -> 동작 흐름 -> 사용 방법 -> 헷갈리는 점 -> 디버깅 체크리스트 -> 관련 문서` 흐름을 기본으로 한다.
- 공식 문서 링크, 이미지 임베드, 엔진 소스 참고 지점은 삭제하지 않고 문서 후반의 참고 영역으로 정리한다.
- 짧은 문서는 추측으로 채우지 않고, 관련 문서 연결과 보강 필요 상태를 남긴다.

## 섹션 사용 기준

| 섹션 | 목적 | 생략 가능 여부 |
| --- | --- | --- |
| `요약` | 첫 화면에서 정의와 쓰임을 복구 | 생략하지 않음 |
| `핵심 결론` | 나중에 반드시 기억할 조건 압축 | 생략하지 않음 |
| `개요` | 기능의 배경과 해결 문제 설명 | 짧은 메모에서도 유지 |
| `작동 모델` | 엔진 객체와 데이터 흐름 설명 | 내용이 없으면 TODO로 표시 |
| `주요 요소` | 클래스, 옵션, 에셋, 상태 비교 | 표가 유용할 때 사용 |
| `동작 흐름` | 실행 순서, 이벤트 순서, 네트워크 경로 | 흐름형 주제에서 사용 |
| `사용 방법` | 에디터/코드 절차 | 순서가 있는 주제에서 사용 |
| `흔한 실수와 안전한 대안` | 비슷한 개념과 오해 분리 | 짧게라도 권장 |
| `디버깅 체크리스트` | 문제 발생 시 확인 순서 | 실무 주제에서 권장 |
| `엔진 소스 참고 포인트` | 읽을 가치가 있는 파일과 이유 | 근거가 있을 때만 사용 |
| `관련 문서` | vault 내부 탐색 연결 | 가능한 한 유지 |

## 문체 규칙

- 첫 문장은 정의, 두 번째 문장은 의미, 세 번째 문장은 실전 맥락으로 쓴다.
- 언리얼 개념, 기능, 에디터 항목, 노드 이름은 첫 의미 있는 등장에 `한글 용어(English Term)`로 병기한다.
- 같은 문서 안에서 한 번 병기한 뒤에는 한글 용어만 사용한다.
- 영어 발음을 한글로 옮기는 것이 아니라, 대응 가능한 한국어 기술 용어를 우선한다.
- `블랙보드 키(Blackboard Key)`, `예측 키(Prediction Key)`, `강 참조(Hard Reference)`처럼 일반 단어보다 구체적인 복합 용어를 우선 병기한다.
- `하드 레퍼런스`, `소프트 레퍼런스`처럼 발음 차용만 한 표현은 특별한 출처 표기나 비교 맥락이 아니면 `강 참조`, `약 참조`로 바꾼다.
- `약 참조`는 문맥에 따라 다르게 병기한다. 에셋 로딩의 soft reference는 `약 참조(Soft Reference)`, 델리게이트/공유 포인터 수명 관리의 weak reference는 `약 참조(Weak Reference)`로 쓴다.
- 함수명, 클래스명, 프로퍼티명, enum 값, 콘솔 명령, 모듈명, 파일 경로는 번역하거나 독음을 붙이지 않고 코드 표기로 둔다.
- 번역체를 유지하되, 너무 직역투로 끊기면 자연스럽게 다듬는다.
- 기능 설명과 의견을 섞지 않는다. 의견은 `주의사항`, `실무 해석`, `관련 문서`로 분리한다.
- 긴 문단은 3~5문장 안에서 끊고, 필요하면 표나 목록으로 바꾼다.

## 표 작성 규칙

다음 항목은 가능하면 표로 정리한다.

- 프로퍼티 목록
- 옵션 목록
- 타입 비교
- 조건 비교
- 장단점 비교
- 클래스 책임 분리
- 네트워크 실행 위치와 권한 조건

```md
| 종류 | 설명 | 언제 쓰는가 |
| --- | --- | --- |
| `COND_OwnerOnly` | owner에게만 보냄 | 개인 정보 복제 |
| `COND_SkipOwner` | owner 제외 전송 | owner는 이미 아는 값 |
```

## Callout 사용 규칙

| Callout | 용도 |
| --- | --- |
| `[!summary]` | 문서 시작 요약 |
| `[!info]` | 공식 문서나 엔진 동작의 중요 포인트 |
| `[!tip]` | 실무 팁, 사용 요령 |
| `[!caution]` | 오해하기 쉬운 제약, 성능 비용, 함정 |
| `[!example]` | 이해를 돕는 예시 |
| `[!note]` | 문맥상 덧붙일 설명 |

## 이미지 사용 규칙

- 공식 문서 흐름을 따라갈 때는 필요한 지점에 이미지를 둔다.
- 이미지 직전 문단에서는 무엇을 봐야 하는지 먼저 적는다.
- 이미지 뒤에는 가능하면 한 줄 해설을 덧붙인다.
- Markdown 원본에서는 Obsidian 이미지 임베드 문법을 사용한다.

## 보강 상태 기준

문서가 완전히 정리되지 않았을 때는 진행 문서에 아래 상태를 남긴다.

| 상태 | 의미 |
| --- | --- |
| `needs-content` | 구조는 있으나 내용이 부족함 |
| `merge-candidate` | 별도 문서보다 관련 문서에 병합하는 편이 좋음 |
| `skipped` | 현재 범위에서 제외 |
| `done` | 구조 정리와 기본 검증 완료 |
