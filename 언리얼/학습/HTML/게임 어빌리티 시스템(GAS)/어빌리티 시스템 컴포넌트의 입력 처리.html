Gameplay Ability System

어빌리티 시스템 컴포넌트의 입력 처리

ASC 입력 처리는 키보드나 패드 입력을 직접 읽는 시스템이 아니라, 이미 들어온 입력을 어떤 Ability Spec에 전달할지 결정하는 라우팅 단계입니다. InputID, AbilitySpec, Pressed/Released 신호, TryActivateAbility의 관계를 분리해 보면 구조가 명확해집니다.

원본: 게임 어빌리티 시스템(GAS)/어빌리티 시스템 컴포넌트의 입력 처리.md 난이도: ASC 입력 흐름 핵심: InputID, AbilitySpecInputPressed, TryActivateAbility 검수 기준: Unreal Engine 5.7.4

한 줄 정의

ASC 입력 처리는 플레이어 입력을 Ability Spec의 InputID와 연결해 GA를 활성화하거나, 이미 활성화된 GA에 입력 상태 변화를 전달하는 흐름입니다. 원본 노트의 InputID, AbilitySpecInputPressed, AbilitySpecInputReleased, TryActivateAbility 연결이 핵심입니다.

입력 시스템과 GAS 입력은 다른 층입니다

Enhanced Input 또는 기존 Input System은 물리 입력을 게임 이벤트로 바꿉니다. ASC는 그 결과를 받아 “이 입력에 묶인 Ability Spec이 있는가”, “이미 실행 중인가”, “새로 활성화해야 하는가”를 판단합니다. 따라서 키 설정은 Input System에서, 어빌리티 실행 가능 여부는 GAS에서 다룹니다.

InputID

FGameplayAbilitySpec에 저장되는 숫자 입력 슬롯입니다. 같은 InputID에 여러 어빌리티가 묶일 수도 있습니다.

Pressed

입력이 눌렸음을 Spec과 활성 GA에 전달합니다. 미활성 상태라면 활성화 요청으로 이어질 수 있습니다.

Released

입력이 떨어졌음을 활성 GA에 전달합니다. 차징, 홀드, 채널링 어빌리티에서 중요합니다.

Confirm / Cancel

Target Actor나 Ability Task가 대기 중일 때 확인/취소 입력을 별도 신호로 보낼 수 있습니다.

입력 Pressed 흐름

입력이 들어왔을 때 ASC는 먼저 해당 InputID에 연결된 Spec을 찾습니다. 이후 활성 중인 어빌리티에는 입력 신호를 전달하고, 아직 활성화되지 않은 어빌리티는 실행 요청을 시도합니다.

1. Input 입력 발생 Input Action 또는 키 바인딩에서 Ability InputID를 결정합니다.
2. Find Spec 검색 ASC에서 해당 InputID를 가진 Ability Spec을 찾습니다.
3. Press Pressed 전달 AbilitySpecInputPressed 같은 경로로 Spec의 입력 상태를 갱신합니다.
4. Active? 활성 여부 판단 이미 활성화된 GA라면 입력 이벤트를 기다리던 Task나 로직이 반응합니다.
5. Activate 새 실행 요청 미활성 상태라면 TryActivateAbility로 발동을 시도합니다.

입력은 발동 조건을 우회하지 않습니다

입력이 들어와도 GA의 태그 요구 조건, 쿨다운, 비용, Net Execution Policy를 통과하지 못하면 활성화되지 않습니다. 입력 처리는 “요청”이고, 실제 실행 가능 여부는 GAS의 활성화 검사에서 결정됩니다.

Released와 홀드형 어빌리티

입력이 떨어졌을 때도 같은 InputID에 묶인 Spec을 찾아 Released 신호를 전달합니다. 이 흐름은 차징 공격, 조준 유지, 채널링 스킬처럼 “누르고 있는 동안” 상태가 중요한 어빌리티에서 핵심입니다.

상황 Pressed에서 할 일 Released에서 할 일
즉발 스킬 미활성 GA를 바로 TryActivateAbility 대개 별도 처리 없음
차징 공격 GA 활성화 후 차징 시작 시간 기록 차징 종료, SetByCaller 값 계산, GE 적용
조준 후 발사 Target Actor/Reticle 시작 타겟 확정 또는 발사 입력으로 해석
채널링 지속 GE 또는 반복 Task 시작 GA 취소 또는 EndAbility로 정리

구현 패턴

5.7 기준으로도 InputID 방식은 여전히 이해할 가치가 있지만, 프로젝트에 따라 GameplayTag 기반 입력 라우팅이나 Enhanced Input Action과 직접 연결하는 구조를 선택할 수 있습니다.

패턴 장점 주의점
InputID 기반 원본 GAS 예제와 FGameplayAbilitySpec 구조를 이해하기 쉽습니다. 숫자 ID만으로는 의미가 드러나지 않아 enum/테이블로 관리해야 합니다.
GameplayTag 기반 Input.Ability.Fire처럼 의미가 명확하고 데이터 주도 설계와 잘 맞습니다. 프로젝트 전용 매핑 계층을 직접 만들어야 합니다.
Enhanced Input Action 직접 연결 입력 값, Triggered/Started/Completed 상태를 세밀하게 다룰 수 있습니다. ASC로 전달할 Pressed/Released/Confirm/Cancel 규칙을 명확히 분리해야 합니다. 
// 개념 예시: InputID로 연결된 Spec을 찾아 입력을 전달하는 형태
void UProjectASC::AbilityInputPressed(int32 InputID)
{
    TArray<FGameplayAbilitySpecHandle> Handles;
    FindAllAbilitiesWithInputID(InputID, Handles);

    for (const FGameplayAbilitySpecHandle& Handle : Handles)
    {
        if (FGameplayAbilitySpec* Spec = FindAbilitySpecFromHandle(Handle))
        {
            AbilitySpecInputPressed(*Spec);

            if (!Spec->IsActive())
            {
                TryActivateAbility(Spec->Handle);
            }
        }
    }
}

5.7 공식 API에서 확인할 점

AbilitySystemComponent에는 InputID로 어빌리티를 찾는 함수와 활성화 요청 함수가 제공됩니다. GameplayAbilityInputBinds는 예제용 enum에 가깝고, 실제 키와 액션 매핑은 프로젝트의 입력 시스템에서 결정합니다.

입력 차단과 게임플레이 차단

ASC에는 로컬 유저의 입력 기반 활성화를 막는 기능이 있지만, 이것을 침묵, 기절, 무장 해제 같은 게임플레이 상태 차단과 혼동하면 안 됩니다.

입력/UI 차단

메뉴가 열렸거나 UI가 입력을 소비하는 상황처럼, 로컬 플레이어 입력을 잠시 막을 때 사용합니다. 공식 API도 이 기능을 게임플레이 침묵/디스에이블 용도로 쓰지 말라고 구분합니다.

게임플레이 차단

기절, 침묵, 쿨다운, 무장 해제는 Gameplay Effect와 Gameplay Tag를 통해 막는 편이 맞습니다. 그래야 서버 권한, 복제, UI 표시, 디버깅이 같은 기준으로 움직입니다.

복습 질문

1. InputID는 어디에 저장되는가?

정답: FGameplayAbilitySpec에 저장됩니다. ASC는 이 값을 기준으로 입력에 맞는 Spec을 찾을 수 있습니다.

2. 입력이 눌렸는데 GA가 아직 활성화되지 않았다면?

정답: 보통 Pressed 신호를 기록한 뒤 TryActivateAbility로 활성화를 시도합니다.

3. Released 신호가 중요한 어빌리티는?

정답: 차징, 조준 유지, 채널링처럼 누르고 있는 시간이 의미 있는 어빌리티입니다.

4. 입력 차단과 기절 상태 차단은 무엇으로 구분하는가?

정답: UI/로컬 입력 차단은 입력 억제 기능으로, 기절/침묵 같은 게임플레이 차단은 GE와 Tag 조건으로 처리합니다.

관련 노트

  • 어빌리티 시스템 컴포넌트(ASC): 입력을 받는 GAS 중심 컴포넌트
  • 게임플레이 어빌리티 스펙(Spec): InputID를 보유하는 등록 단위
  • 게임플레이 어빌리티(GA): 입력으로 활성화되는 실행 흐름
  • 게임플레이 어빌리티 타겟 액터(TA): Confirm/Cancel 입력과 TargetData 흐름
  • 게임플레이 태그(Tag): 입력이 아니라 상태 조건으로 어빌리티를 차단하는 방식
