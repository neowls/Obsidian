모션 매칭(Motion Matching)

Motion Matching은 현재 캐릭터 상태와 목표 궤적을 쿼리로 만들고, Pose Search Database에서 가장 가까운 포즈를 찾아 재생하는 애니메이션 선택 시스템입니다. 전통적인 State Machine 전이 규칙을 줄이고, 많은 애니메이션 데이터를 기반으로 더 반응적인 로코모션을 만들 때 사용합니다.

Pose Search 선택 실험판

Motion Matching은 현재 상태와 미래 궤적을 쿼리로 만들고, Database 후보 중 비용이 가장 낮은 포즈를 선택합니다. 속도와 방향을 바꿔 어떤 후보가 선택되는지 확인하세요.

목표 방향
Runtime Query Speed 420 / Forward Trajectory + Current Pose feature vector

가장 낮은 비용의 후보가 Motion Matching 노드의 출력 포즈가 됩니다.

한 줄 정의

Motion Matching은 애니메이션을 상태 이름으로 고르는 대신, 현재 포즈와 미래 이동 의도에 가장 가까운 데이터베이스 포즈를 비용 계산으로 고르는 방식입니다. Pose Search 플러그인이 스키마와 데이터베이스를 만들고, AnimGraph의 Motion Matching 노드가 런타임 검색과 블렌딩을 담당합니다.

1 플러그인 활성화 Pose Search 플러그인을 켜고 프로젝트를 재시작합니다.
2 Schema 작성 어떤 본, 속도, 궤적을 비교할지 채널로 정의합니다.
3 Database 구성 검색 대상 애니메이션과 검색 모드를 정합니다.
4 AnimGraph 연결 Motion Matching 노드에 Database와 블렌드 설정을 연결합니다.
5 디버깅과 튜닝 Rewind Debugger, 채널 가중치, 노티파이 필터링으로 결과를 다듬습니다.

시각화 요약: Pose Search 데이터 경로

Character Intent 속도, 입력 방향, 원하는 미래 궤적이 런타임 쿼리의 일부가 됩니다.
Current Pose 현재 본 위치와 속도가 전환 비용을 줄이는 기준이 됩니다.
Pose Search Schema 어떤 채널과 가중치로 비교할지 정의합니다.
Search Database 분석된 애니메이션 포즈와 feature vector를 검색 대상으로 보관합니다.
Motion Matching Node 가장 낮은 비용의 포즈를 고르고 블렌드 정책을 적용합니다.
Output Pose 선택된 애니메이션이 AnimGraph의 다음 노드로 전달됩니다.

기존 방식과의 차이

구분 State Machine / Blend Space Motion Matching
선택 기준 상태 전이 조건, 속도/방향 파라미터 현재 포즈, 본 위치/속도, 과거/미래 궤적의 비용
장점 구조가 명확하고 작은 데이터에도 예측 가능 전이 규칙을 적게 작성해도 다양한 상황에 반응
비용 상태가 늘수록 그래프와 전이 조건이 복잡해짐 데이터베이스 크기, 채널 수, 검색 빈도에 따라 CPU/메모리 비용 증가
적합한 경우 명확한 상태와 적은 이동 패턴 방향 전환, 시작/정지, 피벗, 다양한 속도가 많은 로코모션

Pose Search Schema

Schema는 검색에 사용할 특징 벡터를 정의하는 에셋입니다. "어떤 데이터를 비교할 것인가"를 정하는 곳이므로, 부정확한 Schema는 아무리 좋은 애니메이션을 넣어도 잘못된 포즈 선택을 만듭니다.

Trajectory 채널

캐릭터의 과거/미래 이동 궤적을 비교합니다. 로코모션에서는 입력 방향과 목표 이동 방향을 반영하는 핵심 채널입니다.

Pose 채널

발, 손, 골반처럼 중요한 본의 위치/속도/회전/페이즈를 비교합니다. 발 본은 걷기/달리기 품질에 특히 중요합니다.

Heading / Velocity

본이나 캐릭터의 방향과 속도를 비교합니다. 월드 이동보다 캐릭터 로컬 움직임을 보고 싶으면 Character Space 옵션을 고려합니다.

Phase

보행 주기 같은 반복 애니메이션의 위상을 비교합니다. 좌우 발 타이밍이 흔들릴 때 중요한 단서가 됩니다.

채널을 늘리는 것이 항상 정답은 아닙니다

채널과 샘플이 많아지면 검색 품질을 높일 수 있지만, 메모리와 런타임 검색 비용도 증가합니다. 먼저 발 위치/속도와 궤적처럼 결과에 직접 영향을 주는 최소 채널을 잡고, 잘못 선택되는 케이스를 디버깅한 뒤 보강하는 편이 안정적입니다.

Pose Search Database

Database는 Motion Matching 노드가 선택할 수 있는 애니메이션 후보 목록입니다. 원본 노트 기준으로 Animation Sequence를 기본으로 사용하고, 필요에 따라 Animation Composite와 Blend Space도 검색 대상으로 구성할 수 있습니다.

설정 학습 포인트
Schema Database가 어떤 특징 벡터로 인덱싱될지 결정합니다. 다른 Skeleton이나 채널 구조를 섞기 전에 Schema 호환성을 먼저 확인합니다.
Continuing Pose Cost Bias 현재 재생 중인 세그먼트를 유지할지, 더 빨리 다른 포즈로 넘어갈지 조정합니다. 음수는 유지 쪽, 양수는 이탈 쪽으로 작동합니다.
Pose Search Mode Brute Force는 모든 포즈를 평가하고, PCAKDTree는 PCA/KDTree 기반 최적화 검색을 사용합니다. 원본 노트의 VPTree는 실험 기능으로 취급합니다.
Normalization Set 걷기/달리기/전투 이동처럼 성격이 다른 Database를 비교 가능한 범위로 정규화하거나, 상황별 데이터 풀을 제어할 때 사용합니다.
Root Motion 로코모션 Motion Matching에 쓰는 애니메이션은 보통 Root Motion이 필요합니다. 애니메이션 시퀀스의 Root Motion 설정까지 같이 확인합니다.

Motion Matching 노드

AnimGraph의 Motion Matching 노드는 Database 검색, 선택 결과 재생, 블렌드 스택, 노티파이 필터링을 묶는 런타임 진입점입니다. UE 5.7 Python API에서도 AnimNode_MotionMatching은 PoseSearch 플러그인 노드로 노출되며, Database와 검색/블렌드 관련 속성을 갖습니다.

옵션 의미 조정 기준
Database 검색할 Pose Search Database 상황별 Database를 나눈 경우 Anim Node Function이나 Chooser로 교체할 수 있습니다.
Blend Time 새 포즈로 넘어갈 때 블렌드 시간 짧으면 반응이 빠르지만 팝핑이 생기고, 길면 부드럽지만 둔해집니다.
Pose Jump Threshold Time 같은 세그먼트 내 너무 가까운 포즈로 점프하지 않게 하는 시간 범위 작은 떨림이나 같은 클립 반복 선택을 줄이는 데 사용합니다.
Pose Reselect History 최근 선택한 포즈를 일정 시간 다시 선택하지 않게 함 반복적인 포즈 재선택으로 보행이 떨릴 때 확인합니다.
Search Throttle Time 새 검색을 수행하는 최소 간격 매 프레임 검색이 필요 없는 점프/착지류 동작에서는 성능 절약 수단이 됩니다.
Should Filter Notifies 선택 포즈가 바뀌며 같은 Anim Notify가 여러 번 울리는 것을 제한 발소리, 먼지 이펙트 같은 반복 노티파이 중복을 줄입니다.
Max Active Blends Blend Stack에서 동시에 유지할 블렌드 수 0이면 블렌드 스택이 꺼집니다. 값이 커질수록 부드러워질 수 있으나 비용이 늘어납니다.

튜닝 판단 기준

잘못된 포즈가 선택될 때

가중치만 높이지 말고 데이터 자체가 원하는 속도와 방향을 포함하는지 먼저 확인합니다. 이동 모델은 5m/s인데 데이터 평균이 4m/s라면 최고 속도 포즈만 반복 선택될 수 있습니다.

노티파이가 중복될 때

Should Filter Notifies와 Notify Recency Time Out을 사용합니다. 단, Notify State에는 적용되지 않는 점을 구분해야 합니다.

애님 노티파이 필터링 미사용 애님 노티파이 필터링 사용

UE 5.7.4에서 확인할 최신 포인트

UE 5.7 릴리즈 노트 기준으로 Motion Matching과 Chooser 통합이 실험 기능으로 추가되었습니다. 이는 Database 단위뿐 아니라 개별 에셋 단위에서도 게임 로직 조건으로 후보를 필터링할 수 있게 하는 방향입니다. 프로덕션 문서에는 실험 기능으로 표시해 두고, 핵심 로코모션은 기존 Pose Search Database 흐름을 먼저 안정화하는 것이 좋습니다.

실무 체크리스트

  • Pose Search 플러그인이 켜져 있고, 프로젝트 재시작 후 에셋 메뉴가 보이는지 확인합니다.
  • Schema의 Skeleton이 실제 캐릭터 Skeleton과 맞는지 확인합니다.
  • 발 본, 골반, 궤적 샘플처럼 결과에 직접 영향을 주는 채널부터 최소 구성합니다.
  • Database에 시작, 정지, 회전, 피벗, 속도별 루프가 충분히 들어 있는지 확인합니다.
  • Root Motion을 사용하는 로코모션이면 애니메이션 시퀀스의 Root Motion 설정을 일괄 확인합니다.
  • Search Throttle로 검색 비용을 낮추되, 입력 반응성이 떨어지는 지점을 Rewind Debugger로 확인합니다.
  • 발소리나 발 먼지처럼 중복되기 쉬운 Notify는 필터링 가능 여부와 Recency Time을 따로 점검합니다.

복습 질문

Q1. Motion Matching에서 Schema와 Database의 역할은 어떻게 다른가?

Schema는 비교할 특징을 정의하고, Database는 그 특징으로 인덱싱할 애니메이션 후보를 보관합니다.

Q2. 채널 가중치를 올려도 잘못된 포즈 선택이 계속될 수 있는 이유는?

데이터베이스에 목표 속도/방향/상황을 만족하는 애니메이션이 부족하면, 가중치 조정만으로는 올바른 후보가 생기지 않습니다.

Q3. Should Filter Notifies는 어떤 문제를 해결하는가?

포즈 선택이 자주 바뀌며 같은 Anim Notify가 짧은 시간 안에 중복 실행되는 문제를 줄입니다.
