C++ / UObject Reference Internals

UPROPERTY UObject Reference Guide Implementation

이 문서는 UPROPERTY() TObjectPtr<T>와 UPROPERTY() T*의 차이를 엔진 레이어별로 보는 상세 참고 문서입니다. 결론은 동일합니다. GC strong reference 여부는 둘 다 성립하지만, TObjectPtr는 현대적인 엔진 파이프라인과 더 많은 협력 지점을 가집니다.

원본: UPROPERTYObjectReferenceGuideImplementation.md 난이도: 고급 UObject 내부 핵심: ObjectPtr.h, FObjectProperty, GC barrier, Serialization, UHT policy 검수 기준: Unreal Engine 5.7.4

엔진 레이어별 차이

레이어 raw UPROPERTY() T* UPROPERTY() TObjectPtr<T>
UHT / Reflection native pointer member로 파싱되며 object property가 됩니다. wrapper 기반 object pointer member로 인식되어 별도 플래그와 분기 대상이 됩니다.
GC UPROPERTY이면 strong reference로 reference graph에 들어갑니다. 마찬가지로 strong reference이며, 대입/복사에서 incremental GC barrier와 협력할 수 있습니다.
Handle / Resolve resolved UObject* 중심으로 수렴합니다. FObjectPtr / object handle 기반 wrapper 성격으로 editor build에서 lazy resolve와 tracking에 더 적합합니다.
Serialization / Copy 실제 pointer 값을 중심으로 복사/직렬화 경로를 탑니다. wrapper 상태를 보존하는 분기를 탈 수 있어 duplication, reinstancing, placeholder 처리에 유리합니다.
Tooling / Cook dereference 시점을 엔진이 자동 추적하기 어렵습니다. resolve/dereference가 wrapper 경로를 지나므로 access tracking과 cook dependency 분석에 더 잘 맞습니다.

GC와 strong reference

가장 중요한 내부 결론은 UPROPERTY()가 붙은 raw pointer와 TObjectPtr가 모두 GC reference graph에서 객체를 살리는 참조가 될 수 있다는 점입니다. 따라서 "GC 때문에 반드시 TObjectPtr만 써야 한다"는 설명은 부정확합니다.

차이는 업데이트 경로

TObjectPtr는 wrapper 대입과 복사 과정에서 엔진이 object handle과 incremental GC barrier를 연결할 수 있습니다. raw pointer 멤버 대입은 일반 C++ pointer 대입에 가깝기 때문에 이런 협력 지점이 제한됩니다.

Serialization, Copy, Access Tracking

저장 포맷 관점에서 둘은 모두 UObject reference property로 직렬화됩니다. 하지만 FObjectProperty 내부는 property flag와 wrapped pointer 여부에 따라 다른 helper를 사용할 수 있고, TObjectPtr는 unresolved handle이나 editor placeholder 상태를 더 오래 보존할 수 있습니다.

Serialization

둘 다 object reference로 저장되지만, TObjectPtr는 handle-aware 분기를 탈 수 있습니다.

Reflection Copy

raw pointer는 resolved pointer 값으로 수렴하기 쉽고, TObjectPtr는 wrapper 값을 복사할 수 있습니다.

Access Tracking

raw pointer는 단순 C++ read라 추적이 어렵고, TObjectPtr는 resolve/dereference 지점이 명시됩니다.

Cook Dependency

실제 사용된 참조를 분석하는 editor/cook 파이프라인에서 TObjectPtr가 더 현대적인 경로와 맞습니다.

UHT와 팀 정책

최신 UE 코드베이스는 UObject 멤버 선언에서 TObjectPtr를 기본으로 보는 쪽으로 이동했습니다. 기존 raw pointer 멤버가 즉시 잘못된 것은 아니지만, 새 reflected member를 만들 때는 팀 규칙으로 TObjectPtr를 사용하면 리뷰 기준이 단순해집니다. 

// 멤버 strong reference
UPROPERTY()
TObjectPtr<UMyObject> ObjectRef = nullptr;

// 함수 경계와 hot path
UMyObject* GetObject() const
{
    return ObjectRef;
}

void UseObject(UMyObject* Object);

범위를 넓히지 말 것

TObjectPtr는 주로 UPROPERTY 멤버 선언용 기준으로 잡습니다. 파라미터, 반환값, 로컬 변수까지 모두 TObjectPtr로 통일하면 UHT 정책과 일반 UE C++ 관용에서 벗어납니다.

복습 질문

Q1. 내부 구현 관점에서 raw UPROPERTY pointer와 TObjectPtr의 공통 핵심은?

둘 다 reflected object reference이며 GC strong reference 경로에 들어갈 수 있다는 점입니다.

Q2. TObjectPtr의 차이가 가장 의미 있는 영역은?

editor/cook/tooling, access tracking, object handle resolve, incremental GC barrier, property copy/reinstancing 같은 엔진 파이프라인 영역입니다.

Q3. 함수 파라미터와 반환값은 무엇을 쓰는 것이 자연스러운가?

일반 raw T*를 쓰는 것이 UE C++ 사용 패턴에 맞습니다.
