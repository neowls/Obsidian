Gameplay Ability System

게임플레이 어빌리티(GA)의 인스턴싱 옵션

Instancing Policy는 Gameplay Ability가 실행될 때 어빌리티 객체를 어떻게 만들고 재사용할지를 결정합니다. 이 선택은 상태 저장, Ability Task 사용, 동시 실행, 네트워크 복제, 성능에 직접 영향을 줍니다.

원본: 게임 어빌리티 시스템(GAS)/게임플레이 어빌리티(GA)의 인스턴싱 옵션.md 난이도: GA 설계 선택 핵심: NonInstanced, InstancedPerActor, InstancedPerExecution 검수 기준: Unreal Engine 5.7.4

한 줄 정의

GA 인스턴싱 옵션은 어빌리티 실행 상태를 어디에 둘지 정하는 정책입니다. CDO 하나로 처리할지, 액터마다 하나의 인스턴스를 재사용할지, 실행할 때마다 새 인스턴스를 만들지 결정합니다.

기본 판단

특별한 이유가 없다면 InstancedPerActor가 가장 무난합니다. 상태 저장과 복제, RPC, 대부분의 Blueprint/Ability Task 흐름을 다루기 좋기 때문입니다.

NonInstanced

어빌리티 객체를 만들지 않고 CDO에서 실행합니다. 빠르지만 상태 저장과 동적 바인딩이 제한됩니다.

InstancedPerActor

각 액터가 어빌리티 인스턴스 하나를 갖고 실행 간 재사용합니다. 상태가 남으므로 정리가 필요합니다.

InstancedPerExecution

실행할 때마다 새 인스턴스를 만듭니다. 실행별 상태는 깔끔하지만 생성 비용이 가장 큽니다.

옵션 비교

정책 동작 방식 장점 주의점
NonInstanced 인스턴스 없이 Class Default Object에서 실행 객체 생성 비용이 거의 없어 가장 가볍습니다. 멤버 변수 상태 저장, Delegate 바인딩, Ability Task, RPC 같은 기능에 큰 제약이 있습니다.
InstancedPerActor 액터마다 하나의 GA 인스턴스를 만들고 재사용 상태 저장과 복제가 가능하고, 대부분의 어빌리티 구현에 적합합니다. 실행 간 멤버 변수가 남을 수 있으므로 시작/종료 시 상태 정리를 명확히 해야 합니다.
InstancedPerExecution 활성화할 때마다 새 GA 인스턴스를 생성 실행별 상태가 분리되어 변수 초기화 부담이 적고 동시 실행 모델과 잘 맞습니다. 자주 실행되는 능력에는 생성 비용이 부담될 수 있고, 복제 지원 범위도 확인해야 합니다.

선택 기준

아래 질문에 답하면 어떤 정책을 써야 할지 빠르게 좁힐 수 있습니다.

1. State 상태가 필요한가? 멤버 변수, Delegate, Task가 필요하면 NonInstanced는 피합니다.
2. Reuse 실행 간 유지할 값이 있는가? 콤보 단계나 캐시가 필요하면 InstancedPerActor가 맞기 쉽습니다.
3. Isolation 실행별 분리가 중요한가? 동시에 여러 실행이 겹치거나 매번 깨끗한 상태가 필요하면 InstancedPerExecution을 봅니다.
4. Frequency 매우 자주 실행되는가? 수백 개 액터가 반복 실행하면 생성 비용과 상태 제약을 함께 비교합니다.
5. Network RPC/복제가 필요한가? 복제나 Ability 내부 RPC가 필요하면 공식 지원 범위를 확인하고 보수적으로 선택합니다.

실무 기본값

플레이어 스킬, 블루프린트 기반 능력, Ability Task를 쓰는 능력은 대체로 InstancedPerActor부터 검토하는 편이 안전합니다.

NonInstanced 주의

CDO에서 실행되므로 인스턴스별 상태를 둘 수 없습니다. “가볍다”는 이유만으로 고르면 이후 Task, 변수, 예측 로직에서 구조를 다시 바꾸게 될 수 있습니다.

활성화 전 콜백은 인스턴스에서만 돈다고 가정하지 않습니다

5.7의 UGameplayAbility API를 보면 CanActivateAbility, ShouldAbilityRespondToEvent 같은 판단 함수와 OnAvatarSet, OnGiveAbility, OnRemoveAbility 같은 생명주기 콜백은 실제 활성화 인스턴스가 없을 때도 호출될 수 있습니다. 특히 NonInstanced와 일부 실행 전 단계에서는 CDO 기준으로 실행될 수 있으므로 멤버 변수에 플레이어별 상태를 저장하지 않는 습관이 중요합니다.

예시 판단

어빌리티 추천 후보 이유
점프 NonInstanced 또는 InstancedPerActor 별도 상태가 거의 없으면 NonInstanced도 가능하지만, 최근 프로젝트에서는 일관성을 위해 InstancedPerActor를 선택하기도 합니다.
질주 InstancedPerActor 입력 유지, 이동 속도 변경, 비용 소모, 종료 정리가 필요합니다.
메테오 범위 지정 InstancedPerActor 또는 InstancedPerExecution Target Actor, Ability Task, 몽타주/이펙트 대기 등 실행 상태가 필요합니다.
동시에 중첩 가능한 투사체 발사 InstancedPerExecution 검토 각 실행이 독립 상태를 가져야 하면 실행별 인스턴스가 설계를 단순하게 만들 수 있습니다.

복습 질문

1. NonInstanced는 어디서 실행되는가?

정답: 별도 인스턴스를 만들지 않고 Class Default Object에서 실행됩니다.

2. InstancedPerActor의 가장 큰 장점은?

정답: 액터별 인스턴스를 재사용하면서 상태 저장, 복제, RPC 같은 기능을 쓰기 쉽습니다.

3. InstancedPerExecution을 고려할 상황은?

정답: 실행마다 독립 상태가 필요하거나 동시 실행 가능성을 깔끔하게 분리하고 싶을 때입니다.

4. 인스턴싱 정책을 잘못 고르면 어떤 문제가 생기는가?

정답: 상태가 남거나, 상태를 저장할 수 없거나, Task와 복제 제약 때문에 구현 구조를 다시 바꿔야 할 수 있습니다.
