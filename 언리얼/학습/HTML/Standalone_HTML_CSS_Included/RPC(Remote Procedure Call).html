Networking / RPC

RPC(Remote Procedure Call)

RPC는 함수를 로컬에서 호출했을 때 네트워크 반대편의 서버나 클라이언트에서 실행되도록 하는 기능입니다. 상태를 저장하는 도구가 아니라 요청, 응답, 일회성 연출을 전달하는 도구입니다.

원본: RPC(Remote Procedure Call).md 난이도: 중급 네트워킹 핵심: Server, Client, Remote, NetMulticast, Reliable, Ownership 검수 기준: Unreal Engine 5.7.4

RPC 라우팅 실험판

RPC는 호출한 머신, 함수 종류, Actor ownership에 따라 실행 위치가 달라집니다. 아래에서 조건을 바꾼 뒤 호출하면 어느 머신에서 _Implementation이 실행되는지 확인할 수 있습니다.

호출 위치
RPC 종류
Actor 문맥
Authority Server 상태 확정, Server RPC 실행
Owning Connection Client A Owned Pawn의 owner
Relevant Client Client B 소유자는 아니지만 관찰 가능

Owner Client가 Owned Pawn에서 Server RPC를 호출하면 Server에서 실행됩니다.

한 줄 정의

RPC는 Actor 또는 Actor Component에 선언한 네트워크 함수를 호출 위치, 함수 플래그, ownership, relevancy에 따라 원격 머신에서 실행하게 하는 메커니즘입니다. 공식 5.7 문서가 말하듯 RPC는 단방향 호출이므로 반환값을 가질 수 없습니다. 

UFUNCTION(Server, Reliable)
void ServerTryFire();

void AMyCharacter::ServerTryFire_Implementation()
{
    TryFireOnServer();
}

상태는 Replication으로 남긴다

ServerTryFire()는 요청이고, 서버가 줄인 Ammo와 피해를 입은 Health는 replicated state입니다. RPC만으로 영속 결과를 유지하면 late joiner가 현재 상태를 알 수 없습니다.

시각화 요약: RPC 라우팅

Call Site Actor 또는 Actor Component에서 RPC 함수를 호출합니다.
UFUNCTION Flags Server, Client, Remote, NetMulticast와 Reliable 여부가 기준이 됩니다.
Callspace 현재 머신에서 실행할지, 네트워크로 보낼지 판단합니다.
Owning Connection Unicast RPC는 이 연결을 찾지 못하면 의도한 대상에 도착하지 않습니다.
Network Send relevancy, channel, reliable buffer 상태의 영향을 받습니다.
_Implementation 원격 머신에서 실제 함수 본문이 실행됩니다.

RPC 네 종류

Specifier 실행 대상 주 용도
Server 서버 클라이언트가 발사, 구매, 상호작용 같은 요청을 서버에 보낼 때
Client 해당 Actor의 owning client 서버가 개인 UI, 히트마커, 카메라 연출을 특정 owner에게 보낼 때
Remote 호출한 쪽이 아닌 연결 반대편 C++에서 Client/Server 양방향 호출 형태를 단일 함수로 표현해야 할 때. Blueprint에는 노출되지 않습니다.
NetMulticast 서버와 해당 Actor가 relevant한 클라이언트 폭발, 공용 사운드, 짧은 월드 VFX 같은 순간 연출

원본 최신화 포인트

원본은 RPC를 Server, Client, NetMulticast 세 종류 중심으로 설명했습니다. UE 5.7 공식 문서는 Remote RPC까지 포함해 네 종류를 설명하므로, 이 문서에서는 Remote와 실행 매트릭스 관점을 추가했습니다.

Ownership이 RPC를 결정한다

Unicast RPC는 결국 어느 UNetConnection으로 보낼지를 알아야 합니다. Actor의 owner chain을 따라 owning connection을 찾을 수 없으면 Server RPC나 Client RPC가 드롭되거나 로컬 실행으로 끝날 수 있습니다.

Server RPC

클라이언트가 호출하려면 보통 그 클라이언트가 소유한 PlayerController, possessed Pawn, owned Component에서 호출해야 합니다.

Client RPC

서버가 호출할 때 대상 Actor의 owning connection이 있어야 특정 클라이언트로 보낼 수 있습니다.

NetMulticast

서버에서 호출해야 의미가 있고, 모든 클라이언트가 아니라 Actor가 relevant한 클라이언트에게 갑니다.

ActorComponent

Component RPC는 owner Actor의 네트워크 문맥을 타므로, Component 자체보다 소유 Actor를 먼저 확인합니다.

Reliable과 Send Policy

5.7 공식 문서 기준 RPC는 기본적으로 unreliable이며, reliable은 수신 확인 전까지 재전송되고 이후 reliable RPC 실행을 막을 수 있으므로 신중하게 써야 합니다. 또한 RPC는 ERemoteFunctionSendPolicy로 전송 시점을 조절할 수 있습니다.

옵션 의미 사용 감각
Reliable 수신 확인될 때까지 재전송, 순서 보장 장착 확정, 구매 요청, 라운드 시작처럼 잃으면 안 되는 호출
Unreliable 패킷이 드롭되면 실행되지 않을 수 있음 자주 발생하고 조금 잃어도 되는 cosmetic 이벤트
Default 현재 bunch에 직렬화되고 프레임 끝 net update에서 전송 일반적인 RPC 전송 정책
ForceSend 특정 tick 구간에서 즉시 전송해 지연을 줄임 Replication Graph 또는 Iris 조건에서 중요한 저지연 이벤트에 제한적으로 검토
ForceQueue net update 끝에 bandwidth가 남으면 전송 중요도가 낮은 RPC를 뒤로 미루고 싶을 때

검증과 응답

Server RPC는 신뢰할 수 없는 클라이언트 입력이 들어오는 경계입니다. WithValidation을 사용하면 _Validate에서 기본 입력 검사를 수행할 수 있고, 실패하면 호출 클라이언트가 서버에서 끊길 수 있습니다. 다만 실제 게임 규칙 검사는 _Implementation에서도 반드시 수행해야 합니다. 

UFUNCTION(Server, Reliable, WithValidation)
void ServerEquipSlot(int32 Slot);

bool AMyCharacter::ServerEquipSlot_Validate(int32 Slot)
{
    return Slot >= 0 && Slot < MaxSlots;
}

void AMyCharacter::ServerEquipSlot_Implementation(int32 Slot)
{
    if (!CanEquipSlot(Slot))
    {
        return;
    }

    EquipSlotInternal(Slot);
}

응답 패턴

RPC에는 반환값과 out parameter를 쓰지 않습니다. 결과가 영속 상태면 replicated property로 남기고, 즉시 개인 응답이 필요하면 Client RPC로 돌려보냅니다.

복습 질문

Q1. Client가 World placed Door Actor에 직접 Server RPC를 호출하면 왜 실패할 수 있는가?

그 Door Actor를 클라이언트가 소유하지 않으면 owning connection이 맞지 않아 Server RPC가 드롭될 수 있습니다. 보통 Character나 PlayerController에서 요청하고 서버가 Door를 검증합니다.

Q2. Client가 NetMulticast를 호출하면 모두에게 퍼지는가?

아닙니다. 클라이언트에서 호출한 Multicast는 그 클라이언트 로컬 실행으로 끝납니다. 전체 전파는 서버 호출이 기준입니다.

Q3. Reliable RPC를 남발하면 안 되는 이유는?

acknowledgement 전까지 재전송과 순서 보장을 요구해 buffer가 밀리고, 심하면 연결 안정성에 영향을 줄 수 있기 때문입니다.
