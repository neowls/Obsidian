Networking / Overview

언리얼 네트워킹

언리얼 네트워킹은 서버가 진실을 갖고, 클라이언트는 서버 상태의 복사본을 보며, 클라이언트 입력은 RPC로 서버에 요청하는 구조입니다. 네트워크 설계의 핵심은 상태 동기화인 Replication과 원격 함수 실행인 RPC를 정확히 나누는 것입니다.

원본: 언리얼 네트워킹.md 난이도: 네트워크 큰 그림 핵심: Authority, Ownership, Relevancy, Replication, RPC 검수 기준: Unreal Engine 5.7.4

Authority / Ownership / Relevancy 지도

같은 Actor라도 서버 권한, owning connection, relevancy가 다르면 Replication과 RPC의 선택지가 달라집니다. Actor 문맥을 바꿔 어떤 규칙이 성립하는지 확인하세요.

Actor 문맥
Authority Server 상태 변경의 기준
Client A Owner + Relevant Server RPC 진입점 가능 여부를 결정
Client B Relevant 복제/Multicast 수신 가능 범위
상태 변경Replication영속 상태는 서버가 바꾸고 복제합니다.
요청Server RPC 가능Owner Client에서 서버로 요청할 수 있습니다.
개인 응답Client Aowning connection이 있어야 합니다.
공용 연출A, Brelevant client에게만 의미가 있습니다.

가장 먼저 잡을 세계관

Unreal Multiplayer는 서버 권위 모델입니다. 서버가 게임 규칙과 최종 상태를 결정하고, 클라이언트는 자신의 입력을 서버에 전달한 뒤 서버가 승인한 결과를 복제받습니다.

Authority

누가 이 Actor의 진짜 상태를 결정하는가. 보통 서버가 ROLE_Authority입니다.

Ownership

어떤 플레이어 연결이 이 Actor와 연결되는가. Client RPC와 Server RPC의 성립 조건입니다.

Relevancy

이 Actor가 특정 클라이언트에게 지금 복제될 가치가 있는가. Multicast도 이 영향을 받습니다.

Lifetime

Actor가 replicate 중인지, dormant인지, torn off인지, channel이 열릴 수 있는지를 함께 봅니다.

클래스별 역할

클래스 네트워크 관점 역할 자주 하는 실수
GameMode 서버에만 존재하는 게임 규칙 판정자 클라이언트도 알아야 하는 상태를 여기에 둠
GameState 모두가 알아야 하는 매치 전역 상태 서버 전용 규칙 계산까지 과하게 넣음
PlayerState 플레이어별이며 모두가 볼 수 있는 상태 점수/팀/이름을 PlayerController에만 둠
PlayerController owner 전용 입력, UI, Client RPC 진입점 다른 플레이어도 봐야 하는 상태를 여기에 둠
Pawn / Character 월드에서 움직이고 상호작용하는 실제 플레이 객체 클라이언트에서 결과 상태를 확정함
ActorComponent 인벤토리, 무기, 능력처럼 기능별 네트워크 모듈 소유 Actor의 네트워크 문맥을 확인하지 않음

Replication과 RPC의 경계

공식 5.7 문서 기준 RPC는 원격에서 함수를 실행하는 단방향 호출이고, replicated property를 보완하는 장치입니다. 반대로 Replication은 현재 서버 상태를 클라이언트 복사본에 맞추는 시스템입니다.

질문 선택 예시
현재 값이 무엇인가? Replication 체력, 탄약, 문 열림, 점수, 라운드 상태
무언가 해 달라는 요청인가? Server RPC 발사, 재장전, 구매, 상호작용 요청
특정 owner에게만 알려야 하나? Client RPC 히트마커, 개인 UI 응답, 개인 카메라 연출
현재 relevant한 모두에게 순간 연출이 필요한가? NetMulticast RPC 폭발 VFX, 공용 사운드, 짧은 월드 연출
늦게 들어온 플레이어도 알아야 하나? Replication 파괴됨, 점령됨, 이미 열린 문

5.7 보강: Remote RPC

공식 5.7 RPC 문서는 Client, Server, Remote, NetMulticast 네 종류를 설명합니다. Remote는 호출한 쪽이 아닌 연결 반대편에서 실행되는 C++용 unicast RPC이며, Blueprint에는 현재 노출되지 않습니다.

정석 흐름

1 클라이언트 입력 플레이어가 발사, 상호작용, 구매를 시도합니다.
2 Server RPC 소유한 PlayerController, Pawn, Component에서 서버에 요청합니다.
3 서버 검증 거리, 쿨다운, 권한, 자원, 치트 가능성을 검사합니다.
4 상태 변경 서버가 authoritative state를 바꿉니다.
5 Replication / RPC 영속 결과는 Replication, 순간 연출은 필요한 범위에 RPC로 보냅니다.

복습 질문

Q1. 서버 권위 모델에서 클라이언트가 직접 확정하면 안 되는 것은?

체력, 탄약, 점수, 문 열림 같은 authoritative state입니다. 클라이언트는 요청하고 서버가 검증 후 상태를 바꿉니다.

Q2. Multicast가 상태 동기화 대체제가 아닌 이유는?

relevancy 영향을 받고, 늦게 접속한 플레이어에게 과거 호출을 재생하지 않기 때문입니다.

Q3. RPC 실패를 볼 때 가장 먼저 확인할 관계는?

호출 Actor가 replicate 중인지, 그리고 owner chain을 통해 유효한 owning connection을 찾을 수 있는지입니다.
